# 工业级推演系统重构设计

> **版本**: v1.0 (2026-07-31)
> **目标**: 从修补式开发升级为工业级可用系统，95% 可用，有技术壁垒，能创造价值
> **原则**: 不用预设文案假装在工作；要么重试，要么报错说明原因

---

## 一、意图识别（当前不工业级）

### 当前问题
`detectQuestionType` 用正则+LLM分类到13个预设类型，再映射到 `QUESTION_TYPE_TO_DIMENSIONS` 硬编码维度。新领域问题无法处理。

### 重构方案
- 移除 `QUESTION_TYPE_TO_DIMENSIONS` 硬编码映射
- 演直接用 LLM 分析问题，自主生成维度
- 演的 prompt：`分析用户问题，识别核心矛盾，生成3-4个推演维度（名称+视角+需要什么工具+需要什么智囊）`
- 支持任意领域问题，不限于预设类型
- 演可以判断"这个问题我需要先查实时信息"还是"直接召智囊分析"

### 效果
用户问"要不要转行做AI"→演自动生成"职业前景/技能差距/经济风险/个人兴趣"维度，不需要硬编码映射。

## 二、状态机（ReAct 循环）

### 状态定义

| 状态 | 说明 |
|------|------|
| PLAN | 演 Think：分析问题，生成维度，判断信息是否充分 |
| ASK | 演 Ask：追问用户（可一次问多个，不限制字数，只要不废话） |
| EXECUTE | 演 Act：召智囊，每个智囊独立流式发言 |
| REFLECT | 演 Critique：汇总智囊发言，反思，用户可对话 |
| ORACLE | 立卦：基于维度和stance生成卦象 |
| COMMIT | 命签：生成命签文案，保存记忆 |
| PAUSED | 暂停：用户离开，30分钟内可恢复 |
| FAILED | 失败：重试耗尽，显示错误原因 |

### ReAct 循环流程

```
PLAN（Think第1步）
  ├─ 信息不足 → ASK
  │   ├─ 用户回答 → PLAN（Think第2步，基于回答重新分析）
  │   │   ├─ 仍不足 → ASK（第2轮，最多2轮）
  │   │   └─ 充分 → EXECUTE
  │   └─ 用户跳过 → EXECUTE
  └─ 信息充分 → EXECUTE
      ├─ 智囊并行发言（SSE流式）
      ├─ 每1个智囊发言后 → 演 Observe（评估质量）
      ├─ 所有智囊发言完 → 演 Critique
      │   ├─ 需要补充 → 再召智囊（最多1轮）
      │   └─ 充分 → REFLECT
      └─ REFLECT
          ├─ 用户对话 → 演回答
          └─ 用户确认 → ORACLE → COMMIT
```

### 错误处理（不用预设）

```
LLM调用失败
  ├─ 第1次重试（间隔1s）
  │   ├─ 成功 → 继续
  │   └─ 失败 → 第2次重试（间隔2s）
  │       ├─ 成功 → 继续
  │       └─ 失败 → SSE推送错误事件
  │           {"type":"ERROR","stage":"PLAN","reason":"演分析失败","retry":true}
  │           前端显示"演分析失败，[重试]按钮"
  └─ 用户点重试 → 从当前状态重新开始
```

## 三、工具系统（当前不工业级）

### 当前问题
`toolProbeService` 按问题类型硬编码工具选择（city→web_search）。演不能自主决定调什么工具。

### 重构方案
- 演在 PLAN 阶段自主决定需要什么工具
- 演的 LLM 输出包含 `toolNeeds` 字段
- `toolProbeService.probe` 根据演的 `toolNeeds` 调用工具
- 工具结果通过 SSE 实时推送：`{"type":"TOOL_RESULT","tool":"web_search","summary":"..."}`
- 工具失败 → 重试1次 → 报错（不用预设）

### 工具集
- web_search（实时信息）
- weather_query（天气）
- stock_query（股价）
- exchange_rate（汇率）
- salary_calc（薪资计算）
- company_info（公司信息）
- 演可以决定"不需要工具"（纯分析类问题）

## 四、记忆系统（当前不工业级）

### 当前问题
TF 哈希 256 维向量，存在 `.memory-db.json`。不是真向量检索，召回不准。

### 重构方案

| 层 | 存储 | 用途 | 实现 |
|----|------|------|------|
| Working | Redis 或内存 | 当前推演事件流 | EventBus 已实现 |
| Episodic | PostgreSQL + pgvector | 历史推演摘要 | 新增 pgvector 扩展 |
| Semantic | PostgreSQL | 用户命格（决策偏好/性格/价值观） | 已有 user_memory 表 |
| Procedural | PostgreSQL | 推演技巧（什么类型问题用什么维度） | 新增 procedural_memory 表 |

### 关键改动
- `memoryService.recall` 改用 pgvector 真向量检索（替换 TF 哈希）
- 记忆写入时用 LLM 生成 embedding（调 embedding API）
- 召回时用余弦相似度，阈值 0.3+
- 记忆不相关时不召回（返回空，不用预设）

### 降级策略
如果 pgvector 不可用：
- 降级为关键词匹配+LLM 判断相关性
- 不用 TF 哈希（不准）
- 报错说明"向量检索不可用，使用关键词匹配"

## 五、前端交互（当前两套代码混用）

### 当前问题
Game.jsx 同时调 `streamYanChat`（旧轨）和 `startDeliberation`（新轨），状态不一致。

### 重构方案

#### 统一新轨
- 移除 `apiClient.streamYanChat` 调用
- 移除 `inferenceEngine.generateInferenceContent/generateDialoguesForAgents/generateYanSummary` 调用
- 所有 API 调用走 `deliberationClient`
- 演的对话通过新端点 `/api/deliberation/:sessionId/yan-chat`（SSE 流式）

#### 前端阶段

| 阶段 | 说明 |
|------|------|
| casting | 3D动画（等待 API 返回） |
| yan_analyze | 展演分析+追问框（analysis + askUser），用户回答→演二次分析（SSE流式），用户确认→agent_select |
| agent_select | 选智囊（维度匹配预选+市集推荐） |
| agent_debate | 智囊流式发言（SSE token by token），用户可以和智囊对话，演 Observe 评估 |
| summary | 演反思总结（SSE流式），用户可以和演对话 |
| path_reveal | 卦象+命签 |

#### SSE 事件类型

| 事件 | 说明 |
|------|------|
| CONNECTED | 连接成功 |
| THOUGHT | 演 Think 输出 |
| ACTION | 演 Act（调工具/召智囊） |
| OBSERVATION | 演 Observe（工具结果/智囊发言评估） |
| ADVISOR_SPEAK | 智囊发言（流式 token） |
| ADVISOR_ERROR | 智囊发言失败 |
| STATE_CHANGE | 状态转换 |
| ERROR | 错误（含原因和重试按钮） |
| DONE | 推演完成 |

## 七、智囊协作（当前缺失）

### 当前问题
智囊各自发言，没有互参、深挖、质疑。

### 重构方案
- 每个智囊发言后，演可以决定让另一个智囊回应
  - **互参**：风眼说完，演让钱谷评价风眼的观点
  - **深挖**：风眼说了风险，演让风眼深挖具体风险
  - **质疑**：钱谷说"值得"，演让镜渊质疑"真的值得吗"
- 最多1轮互参（避免无限循环）
- 互参发言也通过 SSE 流式推送
- 演的 LLM 输出包含 `nextAction`：`{"action":"critique","agentId":"qiangu","target":"fengyan"}`

## 八、演的自主性判定（AutonomyGate）

### 当前问题
`autonomyGate` 用硬编码规则判断追问/停止，不灵活。

### 重构方案
- 演在每步 Think 后自主决定下一步
- LLM 输出包含 `decision`：`{"action":"ASK|EXECUTE|REPLAN|STOP","reason":"..."}`
- 硬约束（防失控）：
  - 最多2轮追问
  - 最多1次 replan
  - 最多1轮互参
  - 总 token 消耗不超过 50000
- 软约束（LLM 自己判断）：
  - 信息是否充分
  - 智囊发言是否切题
  - 是否需要更多维度

## 九、用户反馈闭环

### 当前缺失
用户对推演结果不满意无法反馈。

### 重构方案
- 命签页面增加 👍/👎 按钮
- 👎 → 弹出"哪里不满意？"选择：维度不全/智囊不相关/分析太浅/卦象不准
- 反馈写入 `user_feedback` 表
- 反馈用于改进：如果某维度频繁被标记"不全"，演在后续推演中加强该维度
- Eval Pipeline 结合用户反馈（人工+自动双轨）

## 十、并发与性能

### 当前问题
单进程 Node.js，没有并发控制。

### 重构方案
- 每个推演 Session 独立（无共享状态，通过 DB 同步）
- LLM 调用并发控制：同时最多 5 个 LLM 请求（防止 rate limit）
- 智囊并行发言：2-3个智囊同时调 LLM，但受并发控制
- BullMQ 处理长时推演（超过 30s 的推演移到后台）
- 前端 SSE 超时 60s 自动重连

---

## 十一、LLM 成本控制

### 当前缺失
没有 token 消耗统计和控制。

### 重构方案
- 每次推演记录 token 消耗（prompt+completion）
- 单次推演上限 50000 tokens
- 超过上限 → 演强制进入 COMMIT（"信息已足够，生成命签"）
- 用户每日推演次数限制（免费用户 3 次/天）
- logger 记录每次 LLM 调用的 token 数和费用

## 十二、测试策略

### 当前缺失
没有 E2E 测试。

### 重构方案
- 单元测试：每个服务函数（planner/autonomyGate/agentEngine/evalPipeline）

## 十五、LLM 模型管理与路由

### 当前问题
`llmRouter.js` 只调一个模型，没有降级策略。

### 重构方案
- 多模型路由：主模型（GLM-5.2）→ 降级模型（备选）→ 报错
- 模型选择策略：
  - 演分析/智囊发言：用高质量模型
  - 问题分类/意图识别：用快速模型
  - embedding：用专用 embedding 模型
- 模型切换通过配置，不改代码
- 每次调用记录模型名+耗时+token数

## 十六、Prompt 版本管理

### 当前问题
prompt 硬编码在 JS 文件里，修改需要改代码重新部署。

### 重构方案
- prompt 抽取到独立配置文件 `server/src/prompts/`
- 每个 prompt 有版本号
- 支持 A/B 测试（两个版本各跑50%流量）
- prompt 变更不重新部署（热加载）
- 日志记录用了哪个版本的 prompt

## 十七、LLM 输出结构化验证

### 当前问题
LLM 返回的 JSON 可能格式不对，`parseDimensionsJSON` 容错但不完善。

### 重构方案
- 所有 LLM 输出用 JSON Schema 验证
- 验证失败 → 重试（prompt 加"请返回合法JSON"）→ 仍失败 → 报错
- 不用预设填充缺失字段
- 结构化输出示例：
  ```json
  {
    "analysis": "租房核心矛盾是预算与通勤",
    "dimensions": [{"name":"财务","perspective":"financial"}],
    "missingInfo": ["预算","工作地点"],
    "nextAction": "ASK"
  }
  ```

## 十八、数据隐私与合规

### 当前问题
用户问题可能涉及敏感信息（健康/财务/情感），没有脱敏。

### 重构方案
- 用户问题存储时脱敏（去掉具体金额/地址/姓名）
- LLM 调用时不传用户身份信息
- 记忆系统只存决策偏好，不存原始问题
- 用户可以删除自己的推演历史
- 隐私政策说明（推演数据如何使用）

---

## 十九、内容安全

### 当前问题
用户输入没有安全过滤。

### 重构方案
- 输入过滤：XSS/SQL 注入防护（已有 `sanitizeLLMText`，需要加强）
- 内容审核：违规内容（暴力/自残/违法）拒绝推演
- 演的 prompt 包含安全边界：不给出医疗诊断/法律建议/投资建议
- 危险问题引导："这个问题建议咨询专业医生/律师"

## 二十、Session 并发安全

### 当前问题
同一个 Session 被多个请求同时操作可能导致状态不一致。

### 重构方案
- Session 操作加乐观锁（version 字段）
- 每次更新检查 version 是否匹配
- 不匹配 → 拒绝更新，返回"会话状态已变更，请刷新"
- SSE 连接限制：每个 Session 最多 1 个活跃 SSE 连接

## 二十一、数据分析与可观测性

### 当前问题
只有 logger 日志，没有结构化数据分析。

### 重构方案
- 推演漏斗分析：输入→追问→选智囊→发言→命签，每步的转化率
- 流失点分析：用户在哪一步离开最多
- 智囊质量分析：哪个智囊的发言被 👎 最多
- 推演时长分析：平均推演耗时，哪些环节最慢
- 数据写入 `analytics_events` 表
- 定期生成报告

## 二十二、多设备同步

### 当前问题
用户在手机上开始推演，电脑上无法继续。

- Session 绑定 userId（不绑定设备）
- 用户登录后在任何设备可以查看/继续推演
- SSE 断线自动重连，从事件流恢复 UI 状态

## 二十三、错误分类与处理矩阵

### 当前问题
所有错误都走同一个 catch，没有分类处理。

### 重构方案

| 错误类型 | 原因 | 处理 | 用户看到 |
|---------|------|------|---------|
| LLM_TIMEOUT | LLM 超时 | 重试2次 | "演思考超时，正在重试..." |
| LLM_RATE_LIMIT | LLM 限流 | 等待3s重试 | "系统繁忙，请稍候..." |
| LLM_INVALID_OUTPUT | LLM 返回格式错 | 重试1次 | "演分析格式错误，正在重试..." |
| DB_ERROR | 数据库错误 | 不重试，报错 | "数据存储异常，请稍后重试" |
| SSE_DISCONNECT | SSE 断开 | 自动重连 | "连接中断，正在重连..." |
| TOOL_ERROR | 工具调用失败 | 重试1次 | "信息查询失败，正在重试..." |
| ALL_RETRIES_FAILED | 重试耗尽 | 报错+重试按钮 | "推演失败：{原因}，[重试]" |

## 二十四、卦象算法

### 当前问题
卦象生成基于维度→八卦映射，可能不够精准。

### 重构方案
- 卦象生成基于多维度加权：
  - 维度 stance 分布（吉/凶/平的比例）
  - 智囊共识度（分歧大→变动卦）
  - 用户命格（历史决策偏好）
- LLM 解读卦象时注入：卦名+卦辞+用户问题+智囊发言摘要
- 卦象不是随机，是基于推演内容的语义映射
