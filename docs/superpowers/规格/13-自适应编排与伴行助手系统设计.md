# 13 · 自适应编排与伴行助手系统设计

## 1. 目标与问题定义

当前 Sandbox 在快问场景存在四个相互放大的问题：路由器过早认定问题类型，任何一次回答都被视为信息充分，快问固定为单智囊，中央对话框遮挡 3D 舞台。结果是“演”看似在对话，实际没有持续理解用户；案卷看似完整，实际把模糊回答当作充分事实；Multi-Agent 看似存在，用户却看不到编排依据和多视角协作。

本设计把 Sandbox 统一成一条可观察、可中断、会根据新信息重新规划的主链：

```text
用户表达
→ 演确认当前理解
→ 编排总管建立信息字段与推演预算
→ 用户一次回答多个关键字段
→ 事实抽取与置信度检查
→ 必要时追问或升级推演深度
→ 用户确认案卷
→ 编排总管公开分派理由
→ 1～6 位智囊协作
→ 反思官检查冲突、证据和遗漏
→ 用户选择路径并生成命签
```

## 2. Agent 边界

### 2.1 用户可感知的系统角色

| 角色 | 职责 | 用户是否直接对话 |
|---|---|---|
| 演·会话主持 | 复述理解、提出追问、接收补充和纠正、解释下一步 | 是，唯一对话入口 |
| 演·编排总管 | 决定深度、信息字段、任务、智囊数量与分派理由 | 通过主持人公开结果 |
| 领域智囊 | 从各自视角形成可追溯发现 | 可被用户点名追问 |
| 反思官 | 检查冲突、证据缺口、重复观点和是否需要重规划 | 只公开检查结果 |
| 审计 Agent | 权限、安全、事件和输出边界检查 | 否 |

智囊路由是编排总管的一项能力，不单独制造一个只会分类的 Agent。快问、标准和深度推演都必须经过同一编排入口；深度路由只提供预算与安全边界，不能提前冻结案卷和智囊池。

### 2.2 多 Agent 不是固定人数

- 快推演：主持人 + 编排总管 + 1～2 位互补智囊；用户能看到为什么没有召集更多人。
- 标准推演：2～4 位智囊，至少覆盖主张视角和挑战视角。
- 深度推演：3～6 位智囊，并启用证据与风险审计。
- 用户补充的信息改变问题类型时，编排总管必须允许 `quick → standard → deep` 升级，并重新生成任务与智囊池。

“要不要吃饭”默认由健康/节律与行为/目标两个互补视角判断；如果用户提到疾病、用药、低血糖或极端节食，进入高风险健康边界，不提供确定性医疗指令。

## 3. 信息收集与开演门禁

### 3.1 字段预算，不是问题次数预算

快问不再使用“回答过一次即完成”。编排总管生成 2～3 个会改变建议的独立字段，并允许用户在一条自然语言里一起回答：

```json
{
  "fieldId": "current_goal",
  "prompt": "你此刻主要是饿、嘴馋，还是在控制体重？",
  "reason": "不同目标会改变是否进食和吃什么",
  "required": true
}
```

“要不要吃饭”的初始字段建议为：当前身体感受、距上一餐与大致摄入、此刻目标。界面可用短问题和选项辅助，但始终允许自由文本。

### 3.2 回答后的重新判断

每次回答必须经过：

1. 提取用户明确说出的事实，不把问题文本或模型猜测写成事实。
2. 对每个字段记录 `confirmed / inferred / unknown / skipped`。
3. 对 `inferred` 保存置信度和推断依据，案卷中与事实分栏显示。
4. 判断新回答是否改变意图、风险或推演深度。
5. 必填字段仍缺失时继续追问；达到体验轮次上限只能请求用户授权“按未知继续”，不能宣称信息充分。

快推演最多两轮对话，每轮可包含多个相关字段。用户可以随时选择“按现有信息继续”，此时未知进入结论条件。

### 3.3 案卷模型扩展

案卷统一显示：

- 已确认：用户明确表达或证据网关接受的事实。
- 系统理解：模型从表达中提取但需要用户确认的推断。
- 仍未知：可能改变建议但用户尚未回答的字段。
- 用户授权假设：用户明确允许系统暂按某个条件继续。

只有必填字段已确认，或用户显式授权未知继续，案卷才能进入 `READY`。

## 4. 编排与重新分派

编排总管输出受控的 `OrchestrationDecision`：

```ts
type InformationField = {
  id: string;
  prompt: string;
  reason: string;
  required: boolean;
  status: 'unknown' | 'confirmed' | 'inferred' | 'skipped';
};

type OrchestrationDecision = {
  depth: 'quick' | 'standard' | 'deep';
  reason: string;
  informationFields: InformationField[];
  tasks: Array<{ id: string; goal: string; perspective: string }>;
  advisors: Array<{ id: string; taskId: string; reason: string }>;
  escalation: { changed: boolean; from?: string; reason?: string };
};
```

选择规则：

1. 每个智囊必须绑定任务，不能只凭人格名称登场。
2. 两位以上智囊必须具有互补视角，重复视角只保留一位。
3. 用户补充改变目标后，未开始的任务可以替换；已完成发现保留但标记旧上下文。
4. UI 公开“为什么召来这些智囊”，不公开提示词和隐藏思维链。
5. 用户可在案卷确认时移除或增加一位候选智囊；安全审计角色不可移除。

## 5. 伴行助手与舞台布局

### 5.1 唯一交互面

中央全屏对话框取消。`演`成为右下角的伴行罗盘，默认保持收起：

- 有新追问时，罗盘展开一条不遮挡主舞台的短气泡。
- 点击罗盘打开伴行栏，所有追问、案卷、事件和插话都在同一线程中。
- 桌面与 iPad 横屏：右侧 360～400px 伴行栏，舞台镜头向左重新构图。
- iPad 竖屏与手机：底部抽屉，默认高度不超过 `42dvh`，可拖动至展开或收起。
- 输入、规划和追问阶段不挂载 3D Canvas；智囊执行阶段才把舞台作为主视觉。

### 5.2 舞台的唯一记忆点

视觉签名为“罗盘召智轨迹”：编排总管确认任务后，任务刻度从伴行罗盘流向主罗盘，不同智囊印记沿固定轨迹入阵。每个印记只表示真实状态：待召、思考、发言、完成、失败。禁止使用与事件无关的粒子、扫描角框和空转动画。

主舞台任何时候至少保留 65% 可视面积。伴行栏打开后不能覆盖当前发言智囊、罗盘中心或下一步主操作。

### 5.3 插话操作

默认只显示一个自然语言输入框。辅助操作位于输入框上方，并使用明确动词和结果说明：

| 操作 | 结果 |
|---|---|
| 补充事实 | 写入案卷，下一轮前重新评估任务 |
| 纠正理解 | 暂停执行，返回案卷确认 |
| 追问智囊 | 选择当前智囊、指定智囊或全部智囊回应 |
| 暂停推演 | 当前安全检查点后暂停，不丢失 Session |

用户首次使用时显示一次简短说明；之后通过信息图标查看，不使用只能 hover 才出现的提示。

## 6. 状态与事件

新增或明确公开事件：

- `UNDERSTANDING_UPDATED`：演更新了对用户目标的理解。
- `INFORMATION_GAP_UPDATED`：字段状态发生变化。
- `DEPTH_ESCALATED`：推演深度因新信息升级。
- `ADVISOR_ASSIGNED`：智囊与任务绑定及公开理由。
- `PLAN_REVISED`：未执行任务被重新规划。

前端动画只消费持久化事件。刷新后通过 Session 快照和事件游标重建伴行线程、智囊状态与当前舞台，不播放已经完成的入场动画。

## 7. 失败与降级

- 信息抽取失败：保留原回答并让用户手动确认，不直接进入 READY。
- 编排模型失败：使用受控字段模板，但 UI 标明“基础编排”，不得伪装成自主 Agent 决策。
- 单智囊失败：显示失败角色与任务，可重试或由编排总管替换。
- SSE 断开：伴行栏显示“正在恢复实况”，业务状态继续由 Session API 确认。
- 3D 初始化失败或设备性能不足：退化为 DOM 智囊阵列，所有操作仍可完成。

## 8. 验收标准

1. “要不要吃饭”初次不得假定用户饥饿；必须收集身体感受、进食间隔/摄入和当前目标中的至少两个字段。
2. 用户回答“刚吃过但超量，想减肥”后，系统识别目标变化并重新判断深度，不得显示“未知 0”。
3. 快推演默认召集 1～2 位互补智囊，并展示每位智囊的任务和入选理由。
4. 案卷严格区分已确认、系统理解和仍未知。
5. 用户能在同一伴行栏完成回答、补充、纠正、追问、暂停和继续。
6. 伴行栏打开时主舞台可视面积不少于 65%，当前智囊与罗盘中心不被遮挡。
7. 1024×768、768×1024、834×1194、1194×834、900×700 和 390×844 全部可完成主链。
8. 刷新后恢复同一案卷、伴行线程、智囊分派和事件游标，不重复执行任务。
9. 自动化测试覆盖信息充分性、深度升级、分派去重、用户中断和响应式布局；真实模型至少连续完成三类问题各三次。
