# 11 · 用户信息案卷与开演门禁设计

> 状态：用户已明确要求继续实施。目标不是增加表单，而是阻止 Agent 在信息不足、记忆未确认时直接分析。

## 1. 用户体验主链

```text
用户提出问题
→ 演复述当前理解
→ 标明推演深度与原因
→ 建立案卷草稿（已知 / 未知 / 待确认记忆 / 暂用假设）
→ 只追问会改变结论的信息
→ 用户回答，案卷实时更新
→ 用户确认案卷和是否采用旧记忆
→ 系统才允许组建小队并执行
→ 推演结论逐项引用案卷信息
```

用户在任何追问中都可以表达“不知道”“不愿回答”“按当前假设继续”。系统必须把它保存为未知或用户授权的假设，不能伪造成事实。

## 2. 自适应信息预算

| 深度 | 适用场景 | 最大追问 | 开演条件 |
|---|---|---:|---|
| 快推演 | 低风险、立即可逆 | 0～1 | 关键身体或时间信号已回答，并确认简版案卷 |
| 标准推演 | 一般取舍、可撤回 | 1～3 | 关键目标、约束和主要反转变量已确认 |
| 深度推演 | 医疗、法律、金融、辞职、重大关系等 | 2～4 | 安全信息和止损条件已确认；未知仍存在时必须显式提示 |

达到轮数上限不等于信息充分。系统可以在用户授权“按假设继续”后开演，但结论必须保留条件和不确定性。

## 3. 权威案卷模型

案卷随 Session 持久化在 `plan.caseFile`，避免新增一套前端事实状态：

```ts
type DecisionCase = {
  version: 1;
  objective: string;
  depth: 'quick' | 'standard' | 'deep';
  depthReason: string;
  facts: Array<{
    id: string;
    question: string;
    value: string;
    source: 'user' | 'tool';
    status: 'confirmed';
  }>;
  memoryCandidates: Array<{
    id: string;
    content: string;
    type: string;
    status: 'pending' | 'accepted' | 'rejected';
  }>;
  assumptions: Array<{
    id: string;
    text: string;
    status: 'pending' | 'accepted' | 'rejected';
  }>;
  unknowns: Array<{
    id: string;
    question: string;
    reason: string;
    status: 'open' | 'skipped';
  }>;
  readiness: {
    status: 'collecting' | 'review' | 'confirmed';
    answeredCount: number;
    maxQuestions: number;
    openUnknownCount: number;
  };
  confirmedByUser: boolean;
  confirmedAt: string | null;
};
```

原始问题是目标，不冒充事实。用户回答是已确认事实。工具结果只有通过 Evidence Gateway 后才能进入事实。历史记忆默认是 `pending`，在用户本局确认前不得进入 Planner 或 Agent 上下文。

## 4. Runtime 门禁

新增 `READY` 状态：

```text
PLAN → WAIT → READY → EXECUTE → REFLECT → ORACLE → COMMIT → COMPLETE
```

- `WAIT`：仍有本轮必须回答的信息。
- `READY`：信息收集结束，但等待用户确认案卷。
- `EXECUTE`：案卷已确认，允许 AgentRunner 工作。
- `/execute` 在 `READY` 时必须返回 `caseConfirmationRequired`，不能偷偷开始。
- `POST /:sessionId/confirm-case` 只接受当前 owner；保存记忆选择与补充说明后将 `READY → EXECUTE`。
- 确认动作幂等；刷新后仍停留在案卷确认，不重复采用记忆。

## 5. 前端呈现

中央案卷确认层只显示本次决策需要的信息：

1. “我理解的问题”与推演深度原因。
2. 用户已经提供的事实。
3. 仍未知但本轮决定不再追问的事项。
4. 召回记忆逐条勾选，默认不采用。
5. 一处补充或纠正输入。
6. “返回补充”与“确认案卷，开始推演”两个明确动作。

左侧事件实况同步显示“案卷草稿形成”“记忆待确认”“用户确认案卷”。中央 3D 只承担状态变化，不承载长文本。

## 6. 安全与降级

- 高风险问题即使达到轮数上限也不得输出确定性医疗、法律或金融指令。
- 用户跳过信息时，案卷保留 `unknown/skipped`，Agent 输出必须说明条件。
- 记忆服务失败时按新用户处理，不阻塞；不得编造历史偏好。
- 案卷确认失败保持 `READY`，允许重试，不进入执行。
- 不在浏览器保存模型密钥、长期记忆全文或内部思维链。

## 7. 验收标准

1. 多轮回答全部保留，后问不能覆盖前答。
2. “要不要吃饭”回答一次后出现简版案卷确认，再进入一位智囊执行。
3. “要不要辞职”至少允许三轮高价值追问，且案卷确认前 `/execute` 被拒绝。
4. 召回记忆默认不采用；只将用户勾选的记忆写入本轮上下文。
5. 刷新 `READY` Session 后仍能看到同一案卷并继续确认。
6. 900×700、1024×768、768×1024 和 390×844 中确认按钮、事实、未知与记忆均可达。
