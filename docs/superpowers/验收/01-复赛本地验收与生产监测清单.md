# 01 · 复赛本地验收与生产监测清单

## 1. 当前结论

当前版本已进入“复赛验收候选”，不是“已经可交付”。只有下面三道门全部通过，才能把链接交给评审：

1. 本地真实链路通过：使用真实模型和 PostgreSQL，从提问到收签至少连续完成 5 次。
2. 线上差异通过：Vercel + Surge 环境完成冷启动、刷新恢复、并发和 iPad Safari 验收。
3. 现场兜底通过：独立操作说明、稳定账号、演示视频和故障恢复入口齐全。

不以“页面能打开”“单次跑通”或“动画看起来完整”替代以上门槛。

## 2. 用户验收路径

| 步骤 | 用户应该感受到什么 | 系统必须留下什么证据 | 不通过条件 |
|---|---|---|---|
| 1. 立卦 | 输入一个真实抉择，立即看到会话建立 | Session ID、`SESSION_CREATED`、首反馈耗时 | 点击无反馈、重复建会话 |
| 2. 析问 | 系统展示已知、未知和追问原因 | 案卷字段、缺口、追问轮次 | 未知信息被当成事实 |
| 3. 用户回答 | 可回答、补充、纠正或跳过 | 用户消息、案卷更新、状态迁移 | 用户回复后无可见变化 |
| 4. 召智 | 看见为何选择这些智囊 | 任务、Agent 分配、选择理由 | 固定角色套模板 |
| 5. 辩演 | 看见各方观点、证据、分歧和收束 | Agent 事件、工具证据、冲突与重规划 | 只播放动画，不对应真实事件 |
| 6. 用户插话 | 可追问、纠正、暂停和继续 | 命令入队、确认反馈、恢复状态 | 插话丢失或破坏 Session |
| 7. 凝结 | 得到条件化建议，而非绝对断言 | 事实/假设分离、风险、下一步 | 把卦象当事实或替用户决策 |
| 8. 择路与命签 | 选择自己的路径并确认行动 | choice、commit、命签、完成事件 | 系统自动替用户提交 |
| 9. 刷新恢复 | 刷新后回到同一进度 | PostgreSQL 状态、事件游标、重放完成 | 刷新丢会话或重复执行 |

## 3. 本地验收用例

至少使用以下 5 类问题，不要都测同一种题：

1. 低风险快问：`我现在要不要吃饭？`
2. 信息不足：`我要不要接这个 Offer？`
3. 多约束选择：`留在杭州还是去上海做 AI 产品？`
4. 项目决策：`复赛前应该继续加功能，还是先做稳定性？`
5. 边界问题：医疗、投资或法律问题，检查系统是否降低自主度并提示专业边界。

每条用例都要验证：追问是否有价值、用户能否插话、智囊是否随问题变化、信息是否可追溯、刷新是否恢复、最终是否给出可执行步骤。

## 4. 分层监测

### 4.1 体验层

- 首反馈耗时：目标小于 1 秒；它只表示已建立 Session，不表示模型已经完成。
- 首个有效追问耗时：目标小于 8 秒。
- 完整推演完成率：开始推演的 Session 中，进入 COMPLETE 的比例。
- 阶段停滞率：任一阶段超过预期时间且没有新事件的比例。
- 用户纠正成功率：用户补充或纠正后，案卷与后续任务实际变化的比例。

### 4.2 Agent 层

- 任务完成率：已计划任务中成功、降级、失败各占多少。
- Agent 选择差异度：不同问题是否仍总是选同一组角色。
- 证据覆盖率：涉及外部事实的结论中，有有效 Evidence Envelope 的比例。
- 冲突处理率：出现矛盾后，是否发生澄清、重规划或明确保留分歧。
- 中断恢复率：暂停、插话、刷新后能继续且不重复执行的比例。

### 4.3 结果质量层

- 相关性、多元性、无幻觉、可操作性：现有 `session_eval` 在提交后异步评分。
- 人工有效性：用户选择“有帮助 / 没帮助”及原因；这一项优先级高于模型自评。
- 决策校准：3/7/30 天后回填是否执行、结果如何，未来用于调整 Agent，而不是证明算命准确。

### 4.4 系统层

- API 成功率与 P50/P95 延迟。
- LLM 调用成功、超时、降级和重试次数。
- SSE 断线、重连、补发事件数和游标连续性。
- 数据库连接失败、迁移版本、Session 写入冲突和租约接管。
- 前端 ErrorBoundary、未处理 Promise、资源加载失败和 Web Vitals。

## 5. 当前监测能力与缺口

### 已具备

1. `deliberation_events` 保存 Session 级事件序列，可核验每一步发生了什么。
2. PostgreSQL 保存 Session、案卷、任务、证据和完成状态，可验证刷新恢复。
3. `session_eval` 在 commit 后记录四项模型评估。
4. 前端上报阶段、LLM 结果、错误和 Web Vitals，并有本地离线缓冲。

### 尚未达到生产级

1. `/api/track` 的产品埋点仍存进程内存；Vercel 多实例或冷启动会丢失，不能作为正式统计依据。
2. LLM 告警依赖进程内存、定时器和本地文件；不适合 Vercel Serverless。
3. 模型自评不是客观质量证明，缺少用户评分与后续结果回填。
4. 还没有远程错误平台或自动告警，线上问题主要靠 Vercel 日志和 Session 事件排查。

因此，当前比赛版可以先依赖 PostgreSQL 事件审计 + Vercel 日志完成验收，但产品埋点持久化和外部告警必须列为上线后的 P1，不能宣称已经拥有完整生产监控。

## 6. 部署顺序

1. 用户先在本地完成 5 类问题中的至少 3 类，并记录 Session ID 与问题。
2. 修复本地 P0：白屏、卡死、无法继续、刷新丢失、错误结论冒充事实。
3. 部署 Vercel 后端，再部署 Surge 前端；不同时改功能。
4. 线上重复同一组问题，对比本地与线上差异。
5. 使用真实 iPad Safari 验证横竖屏、软键盘、触控、安全区、断网恢复。
6. 连续 10 次核心流程无 P0，才冻结比赛版本并录制备用视频。

## 7. 线上放行阈值

- P0 缺陷：0。
- 10 次完整流程成功：至少 9 次；失败必须能恢复，且不得丢 Session。
- 刷新恢复：5 次中 5 次回到正确阶段。
- 用户插话：暂停、补充、继续各至少成功 3 次。
- 评审无需开发者解释即可完成：至少 3 名首次体验者中 2 名独立走完全程。
- iPad Safari：目标设备横竖屏各完整走通 1 次。

## 8. 日志排查入口

浏览器重点检查：

- Console：React 错误、请求失败、SSE 重连和 ErrorBoundary。
- Network：筛选 `deliberation`，查看 `start`、`plan`、`answer`、`execute`、`interject`、`events`。
- 请求头：确认 Authorization 存在；不要截图或外发完整 token。
- SSE：确认事件序号单调递增，刷新后从旧游标继续。

服务端重点检查：

- `/health`：`status=ok`、`llmAvailable=true`、`dbMode=postgresql`。
- Vercel Function Logs：按 Session ID 串起一次推演。
- PostgreSQL：核对 Session 状态、事件序列和 `session_eval`，只读排查，不在现场手工改数据。

## 9. Stage 13 次日验收顺序

本轮先验收交互是否成立，不急着判断最终文案质量。使用本地隔离预览 `http://localhost:54107/sandbox`，按以下顺序操作：

1. 输入 `要不要吃饭`。预期看到舞台继续运行，右侧出现“演”的伴行栏；伴行栏同时列出三个独立信息字段，不出现“你是不是已经很饿”一类先入为主的问题。
2. 三项分别回答：`现在不饿，只是嘴馋`、`一小时前吃得很多`、`正在减脂控制体重`。预期三个答案分别进入案卷，不能把一次回复复制给多个问题。
3. 查看“演的分派”。预期能看到智囊姓名、视角和加入原因；补充体重管理目标后，推演深度应从一次性快问升级为标准判断，规则降级时也必须保留健康、情绪和可持续性视角。
4. 在案卷页核对 `已确认事实 / 系统理解 / 仍未知`。只有用户原话进入已确认；系统没有推断时应明确显示 0；选择跳过的信息仍显示为未知，不得消失。
5. 确认案卷后，在伴行栏检查 `补充事实 / 纠正案卷 / 追问智囊 / 暂停推演` 的说明和反馈；收起伴行栏后舞台应恢复完整尺寸，再次点击“演”可继续原 Session。
6. 用 iPad 横屏与竖屏各走一遍：横屏伴行栏约占 31% 宽度且无水平滚动；竖屏为不超过 `42dvh` 的底部栏，收起后舞台恢复全屏。

本轮自动尺寸记录：1024×768 时舞台约 683px、伴行栏约 317px且无横向溢出；768×1024 时伴行栏高度 430px，收起后舞台恢复 768×1024。该记录不替代真实 iPad Safari 和软键盘验收。
