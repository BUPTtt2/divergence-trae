# 演策多人上线与商业运营收口设计

## 1. 决策与状态

- 决策：以 `codex/deployed-643159-baseline` 为唯一发布源码，完成多人公开使用所需的真实性、数据完整性、可靠性、运营可观测和部署一致性收口。
- 当前状态：设计已形成，等待用户复核后进入实施计划。
- 目标交付级别：Release Candidate，随后进入受控 Production Learning。
- 当前 Gate：CONDITIONAL。源码基线已可追溯，但线上后端可达性、完整回放、离线补传、全站真实数据和依赖风险仍未闭环。

## 2. 已确认事实

核验时间：2026-08-17。

- 当前前端线上版本为 Surge 指纹 `643159`，后端为 `yance-bagua-engine.vercel.app`。
- 当前网络访问 Vercel 后端健康检查超时；前端会从“账号加载中”退回匿名本地状态。
- 当前发布代码已经具备匿名身份、服务端管理员鉴权、`/ops`、行为事件、反馈、部分失败事件和命牌 3D 呈现。
- 当前命牌云端合同没有保存完整澄清、逐轮智囊发言、路径选择与行动承诺，跨设备回放会丢内容。
- `persistDecisionCard` 在云端失败时仅保留本机副本，没有持久化补传队列。
- Calendar 只跳转 `/cards`，不能定位并打开具体记录。
- Scenarios 的初始问题只通过路由内存传递，刷新会丢失尚未创建的推演草稿。
- 成就与自定义智囊均存在两套数据来源。
- 首页及多个页面仍有“剧本”、假 ICP、MIT/Open Source、示例命签或 Demo memory 等不适合商业上线的内容。
- 管理员和公开评委入口已经分离；公开体验不要求注册。

## 3. 方案比较与选择

### 方案 A：只补当前 Surge + Vercel 缺陷

优点是改动少、发布快。缺点是继续保留两套发布渠道、跨域配置与源码漂移风险，不适合作为长期商业基线。

### 方案 B：Vercel 单一发布链路（采用）

前端与后端都由 Vercel 管理；前端通过同源 `/api`、`/health` 和 `/track` 代理到后端。先发布 Preview，验收通过后再替换正式入口。当前 Surge 版本只在切换期作为回退，不再作为长期发布源。

优点是发布、回滚、环境变量、Preview 验收和版本追踪统一。限制是 Vercel 默认域名在部分国内网络仍需要代理；没有自有域名时不能承诺国内裸网稳定访问。

### 方案 C：同时引入邮件、QQ、微信和支付

当前不采用。邮箱验证需要发信域名及邮件供应商；QQ/微信登录需要开放平台应用、主体资质、审核和正式回调域名；支付还需要商户与合规材料。现在接入会形成不可验收的半成品。

## 5. 真实数据与全站页面合同

所有页面遵守以下规则：

1. 用户数据区只展示真实用户数据；没有数据时显示明确空状态。
2. 教学内容可以保留，但必须标注“示例问题”或“预设推演”，不得伪装为用户记录、实时人数或真实成功案例。
3. 运营数字只能来自服务端聚合；获取失败时显示“暂无可验证数据”，不能显示随机数或静态增长率。
4. Agent 预设文本必须标注为“本地演示/规则生成”，不能标注为模型实时分析。
5. 禁止假备案号、假许可证状态、假社区用户、假在线剧本数和未来日期记录。

### 5.1 页面审计矩阵

| 路由 | 上线数据规则 | 必做改动 |
|---|---|---|
| `/` | 产品说明可使用明确标注的预设问题；统计必须来自运营聚合 | “剧本”统一为“预设推演”；删除假 ICP/MIT；删除静态实时统计或接真实接口 |
| `/daily` | 仅展示真实日期、真实签到和真实每日内容来源 | 删除假备案；后端失败显示状态，不伪造用户连续签到 |
| `/scenarios` | 场景属于编辑维护的预设推演，不是假用户案例 | 统一术语；保存场景草稿；删除假备案 |
| `/sandbox` | 真实 Agent 与明确本地演示严格区分 | 后端不可用状态、逐智囊失败、重试、会话恢复、完整命牌 |
| `/agents` | 官方智囊来自服务端 catalog；自定义智囊来自统一目录 | 合并本地/云端数据源，创建后实时出现并可参与推演 |
| `/cards` | 只展示用户真实保存记录 | 删除示例命签；支持精确定位、完整回放、PNG 导出和同步状态 |
| `/community` | 没有真实社区数据时显示空社区 | 删除本地伪社区/假热度/假备案；发布和互动必须是服务端真实写入或暂时关闭 |
| `/calendar` | 基于真实命牌及回访索引 | 精确跳转具体命牌；局部云端失败保留真实本机记录 |
| `/dictionary` | 词条属于静态知识内容 | 保留内容，但去除会被误认为实时模型或用户数据的表述 |
| `/ops` | 仅管理员可见真实聚合 | 增加健康、漏斗、失败、同步、回放完整性和版本维度 |
| `/legal`、`/privacy` | 与实际收集和保留规则一致 | 更新匿名标识、账户、事件、反馈、保留期限和删除说明 |

后台的 `mcpService` mock 工具继续保持 `agentAccessible: false`，不能进入生产 Agent 工具选择。旧 `/api/yan` mock 回复不得作为默认生产对话入口；若已无消费者则删除，否则显式返回 `DEMO_ONLY` 状态。

## 6. Agent 运行时可靠性

### 6.1 可用状态

运行时统一为四种状态：

- `READY`：后端健康且可创建真实推演。
- `DEGRADED`：部分能力不可用，但已有真实本地记录仍可读取。
- `OFFLINE`：不能创建真实 Agent 推演；允许浏览静态产品信息与本机真实记录。
- `RECOVERING`：正在重试或恢复会话。

页面不再展示原始网络错误。用户能看到“发生了什么、刚才输入是否保留、可以做什么”。后端不可用时不得静默走完整套预设流程并让用户误以为是实时 Agent。

### 6.2 智囊部分失败

- 每位智囊显示 `queued/running/completed/failed`。
- 失败保留已完成智囊的真实发言。
- 用户可以只重试失败智囊、替换失败智囊或返回智囊会。
- 达不到贡献门禁时不生成正式命牌。
- 预设模板仅能在用户主动进入“本地演示”时使用，并带来源标记。

### 6.3 场景和会话恢复

- 场景入口把 `scenarioId`、`initialQuestion`、标题和写入时间保存为 session draft。
- 创建服务端 session 后，将 draft 绑定到 session ID。
- 刷新优先恢复服务端 session；尚未创建 session 时恢复未过期 draft。
- 新开一局只清理当前 active session，不删除历史命牌。
- 共享设备交接继续清除访客身份和草稿，但保留设备设置。

## 7. 命牌与完整回放

### 7.1 视觉与交互

- 最终命牌继续浮现在 3D 推演台中，使用真实卦象、路径、总结、行动承诺和智囊信息。
- 参考主仓库改动中的方向：删除示例命签、从日历精确定位真实命签、卦象图标使用八卦符号。
- 不照搬其中的固定 450ms 延时或注释式补丁；使用路由查询参数和渲染完成状态定位。
- 新 Agent 最终案卷和命签册共用同一命牌 presentation model。
- 最终页提供“导出命牌 PNG”“查看完整过程”“存入命牌库”“新开一局”。

### 7.2 回放 V2 数据合同

每张命牌至少关联：

- `sourceSessionId`、`schemaVersion`、`createdAt`、`releaseId`；
- 用户原始问题、场景来源；
- 澄清问题和用户回答；
- 选中的智囊及每轮真实发言、失败状态和来源；
- 分歧、共识、证据引用、路径选项和最终选择；
- 卦象、命牌文案、行动承诺、反馈和回访结果；
- 完整性状态 `complete/partial/local_only`。

云端使用结构化 JSON 快照或独立 replay 表保存，不能继续把完整过程压缩成最多 80 字的 `agentNotes`。旧命牌继续可读，显示“历史记录不含完整过程”。

### 7.3 本机保存与自动补传

- 每张本机命牌带 `syncState: pending/syncing/synced/error` 和稳定幂等键。
- App 启动、恢复联网、登录成功和用户主动重试时刷新 outbox。
- 成功后合并服务端 ID，不产生重复命牌。
- `/ops` 只收集数量、延迟和错误码，不上传命牌正文。

## 8. Calendar、成就与自定义智囊

### 8.1 Calendar

- 日历条目保存 `linkedCardId`。
- 点击真实命牌跳转 `/cards?card=<id>&view=replay`。
- Collection 加载并合并本地/云端后定位该 ID；不存在时显示“记录仅存在于另一设备或尚未同步”。

### 8.2 成就

- 建立一个 achievement repository，统一 stats、unlock 和 XP。
- 首次加载迁移旧 `userStats.js` 与 V2 数据，取最大可信进度并写入迁移版本。
- 页面只从统一 repository 读取，避免“已解锁但图标不亮”。
- 成就不参与真实决策结果，不向运营后台上传具体问题。

### 8.3 自定义智囊

- 服务端 advisor catalog 是登录用户的权威来源。
- 匿名用户可以创建本机 draft；注册/登录后显式迁移到账号。
- 创建、修改、删除通过同一 repository 广播状态，Agents、Community、CouncilWorkbench 和推演台立即刷新。
- 推演请求必须携带完整 advisor contract 或服务端 advisor ID，不能只传一个本地 ID 后让后端找不到。
- 自定义智囊参与分析时使用相同失败、预算、来源和审计合同。

## 9. 运营、商业化与隐私

### 9.1 `/ops` 指标

新增或补齐以下只面向管理员的指标：

- UV、匿名/登录用户比例、版本和入口来源；
- 首页 → 开演 → 澄清 → 智囊会 → 路径 → 命牌 → 保存 → 回访漏斗；
- 每阶段耗时、退出率和恢复成功率；
- 后端健康率、请求超时率、智囊失败率、失败重试成功率；
- 本机保存比例、outbox 数量、同步成功率和同步延迟；
- 命牌回放完整率、PNG 导出率、回访完成率；
- 场景使用率、自定义智囊创建率和实际参议率；
- 反馈分布、低分原因、错误码和 release ID。

禁止在运营事件中上传问题正文、澄清回答、命牌正文、邮箱、昵称和头像。反馈文本单独存储并按既定期限保留。

### 9.2 商业化准备度

本轮不制作支付和订阅 UI。先建立商业化所需的可验证基础：

- 账号与匿名体验边界清楚；
- 使用量、成功率、成本和复访可计量；
- 每次 LLM 请求记录 provider、model、成功、耗时、重试和可用 token/cost；
- 服务端具备按用户和匿名设备的限流，但不妨碍一局正常体验；
- 法律与隐私说明和实际数据合同一致；
- 后续套餐只基于可计量能力设计，不能先做假会员等级。

### 9.3 认证扩展边界

- 当前保留匿名体验和邮箱密码账户。
- 邮箱验证码等拥有域名、发信服务、回调和隐私说明后再接入。
- QQ/微信登录等拥有开放平台应用、主体审核和正式回调域名后再接入。
- 用户曾在聊天中暴露的密码不得进入代码、文档、日志或测试，正式使用前必须更换。

## 10. 错误处理与安全

- 对网络、鉴权、限流、超时、会话过期、部分智囊失败和持久化失败使用统一错误分类。
- 只有幂等读请求和幂等写入允许自动重试；创建会话、保存命牌和反馈必须携带幂等键。
- 管理员权限只由服务端判断；前端隐藏 `/ops` 不是安全边界。
- 所有用户文本做长度限制、输出编码和日志脱敏。
- 不运行破坏性依赖自动修复；逐项确认漏洞可达性和兼容升级路径。
- 数据迁移必须可重复、可回滚，并在 Preview 数据库或内存数据库验证。

## 11. 测试与发布验收

### 11.1 自动化

- 所有行为修改使用测试先行。
- 前端：数据 repository、路由恢复、outbox、回放合同、错误状态、成就迁移、自定义智囊同步。
- 后端：cards/replay schema、幂等补传、管理员指标、隐私字段白名单、限流、部分智囊失败。
- 契约：旧命牌兼容、完整 replay V2、API 错误分类。
- 全量测试、lint、build、依赖审计和 Git dirty check。

### 11.2 浏览器与设备

- 桌面与 390×844 手机视口遍历所有路由。
- 匿名用户完成一局真实推演；后端失败时验证不会伪装成功。
- 刷新恢复场景草稿、进行中 session 和最终命牌。
- 模拟离线保存命牌，再恢复联网补传且无重复。
- 日历打开具体命牌，完整回放并导出 PNG。
- 自定义智囊创建后立即出现并完成一次真实参议。
- 管理员手机打开 `/ops`，普通用户访问得到 403。

### 11.3 发布顺序

1. 本地测试与构建通过。
2. Vercel 前后端 Preview 部署。
3. Preview 完成桌面、手机和真实 Agent 闭环。
4. 进行小规模并发和超时验收。
5. 用户确认后发布 Production。
6. 验证 deployment ID、release ID、哈希、健康、事件和回滚入口。
7. 观察至少一个真实体验批次后再移除 Surge 回退。

## 12. Gate 标准

Release Candidate Gate 只有同时满足以下条件才 PASS：

- 所有页面不存在未标注 mock、假运营数字、假用户记录或占位备案；
- 真实 Agent 成功、失败和本地演示来源可区分；
- 完整回放、离线补传、日历定位和命牌 PNG 在 Preview 验收通过；
- 管理员指标可解释访问、漏斗、失败、成本、同步和反馈；
- 后端历史测试失败已修复或以被批准的语义更新测试；
- 高危依赖完成可达性判断，关键可达风险已升级或缓解；
- Preview 的手机与桌面核心业务闭环均有当前证据；
- 有明确 Production 回滚版本。

## 13. 非目标与禁止动作

- 本轮不接支付、不造会员权益、不伪造邮箱验证码、不申请 QQ/微信开放平台。
- 不整体合并旧主仓库 UI 改动。
- 不删除用户现有主仓库改动或终止其他项目进程。
- 未经用户确认 Preview 结果，不覆盖现在线上入口。
- 不把预设内容包装为实时 Agent 结果。

## 14. 最短下一步

用户确认本设计后，编写分阶段实施计划。第一阶段优先完成：唯一 Vercel 发布配置、固定端口、全站 mock 清理、真实运行时状态、场景恢复、命牌回放 V2 与同步 outbox；随后处理成就、自定义智囊、运营指标和发布验收。
